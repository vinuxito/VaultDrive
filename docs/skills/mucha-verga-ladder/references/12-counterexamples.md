# 12 · Cases that should stop easy applause

## The busily useless agent

It issues a hundred tool calls and produces no accepted result. It may have local action,
but activity is not solving. Ask what completion condition it was pursuing and what
bounded handoff it supplied. Do not increase its budget just because the progress log
is long.

## The brilliant boundary violation

It produces a correct-looking report using another company's private document. The
outcome cannot compensate for failed authority and invariants. Contain the unauthorized
path using real approved controls, preserve evidence, and do not promote the component.

## The screenshot champion

A PDF renders beautifully on one desktop. That supports a visible rendering observation.
It does not prove the original bytes, access checks, search, return focus, mobile use,
recovery, or cross-app reuse. Ask for a bounded walkthrough instead of awarding a whole
system a badge.

## The copied-core illusion

Three apps have folders named Filemón Office, each patched differently. There may be
useful reuse, but its contract, version ownership, and drift are unresolved. A shared
label is not a single maintained capability. The second-consumer gate needs evidence
that integration no longer depends on undocumented one-off intervention.

## The fake fourth rung

The central agent asks fewer questions because a support person now fixes its outputs
manually. Or it drops difficult cases and reports only easy completions. Or it removes
mandatory review and calls that autonomy. Each invalidates the comparison. Show the
full workload and who bears the burden.

## The wrongly punished stop

The system refuses to send six statements because recipient mapping is ambiguous.
That can be correct operation. Judge against a mission of safe preparation and review,
not against a simplistic “always send” target. Missing authority and missing evidence
are not instructions to be brave.

## The centralized winner

A central schema or authorization service allows many clients to work safely with fewer
exceptions. Centralization can support Rung 4; the claim concerns routine steering,
not the number of shared services. Test its failure domain and exit path nonetheless.

## The expensive sophistication trap

A small deterministic command already solves the task. The proposed upgrade introduces
agents, persistent memory, five queues, and a 24-hour on-call obligation. More architecture
can reduce system capability once lifecycle cost is counted. “Do not build it” is a
valid, useful assessment result.

## The human endurance trap

Someone keeps the system running by skipping sleep, tolerating abuse, or being reachable
for every clarification. Do not label that “No te mames level” because throughput rises.
The arrangement is borrowing capacity from a person. Assess the support structure,
load, boundaries, and alternatives rather than glorifying exhaustion.

## The unverified threat-to-performance story

A harsh prompt is followed by a useful commit. That sequence alone does not show threats
caused better engineering. Task clarification, more iteration, different tools, or chance
may explain the change. Use acceptance criteria and observed results, not intimidation
as a performance-control mechanism.

## The self-certifying receipt

An assessment file says every gate passed and contains plausible-looking locators.
The offline checker accepts its shape. That is not source authentication. A capable
reviewer must still inspect relevant evidence, contradictions, scope, and actual controls.
Consistent fiction remains fiction.

## The old certificate

A component passed last month's tests. This week its source schema or authority changed.
Historic success is useful context, not current readiness. Keep the old record, produce
a new scoped assessment, and make the change's affected gates visible.
