# ABRN Drive: user-facing trust claims and their contracts

Updated 2026-09-16 during coherence iterations 5–6. This table describes implementation contracts, not an independent cryptographic audit. Production deployment must be checked separately from repository and private-stage evidence.

| User question / claim | Actual contract and evidence source | Interface wording / limitation |
| --- | --- | --- |
| Is my file encrypted? | Browser upload encryption in `vaultdrive_client/src/pages/files.tsx`, public sender pages and `src/utils/crypto.ts`; encrypted bytes stored by upload handlers. | Contents are encrypted before upload. Names, sizes and access metadata are visible to the service. A failed status lookup establishes no access or protection conclusion. |
| Are keys exclusively in my browser? | Secure Drop recovery in `handle_drop.go` includes server-managed delivery-key recovery. Other browser key paths do not erase this exception. | Explain the Drop exception in Help, onboarding, trust details and public flow guidance. Do not claim universal zero knowledge. |
| Who can read this? | `handle_access.go` access/trust entries; direct `file_access_keys`, file links, group associations and folder permissions have different semantics. | Exclude owner and Secure Drop intake from external read-route counts. Group association is not proof that every member has a usable decryption key. Report the latest successful access snapshot; errors remain unknown. |
| Does a count prove someone read my file? | A public authorized fetch consumes a link allowance before streaming in `handle_public_share_links.go`. | Say authorized fetches, not confirmed reading. A use can be consumed when delivery is interrupted. |
| What does single use do? | Atomic eligibility/consumption check in the public file download handler. It closes permission; it does not delete browser-held keys or existing copies. | Link allowance consumed. Ask the owner for a new link after an interrupted consumed delivery. Never say the file or key was shredded. |
| What does revoke close? | Individual file/folder link handlers close the owned link. File `revoke-external` closes direct recipient keys and public file links; folder access is a separate scope. | Name the scope before confirmation and after server confirmation. Previously downloaded copies and in-progress streams cannot be recalled. Never infer owner-only access from a successful scoped revoke. |
| Was revocation successful? | A successful mutation response is required. A later successful GET cannot turn a rejected DELETE into success. | On rejected/lost responses say unconfirmed, offer access refresh, and avoid automatic replay. Failed refresh after confirmed mutation is a stale list, not a failed mutation. |
| Did the upload arrive? | An explicit accepted upload response confirms storage. Lost post-send response is ambiguous without an immutable receipt lookup. | Separate confirmed, retryable and unconfirmed files. Hold unconfirmed files for recipient/owner review; no filename-based success claim or blind re-upload. |
| Is this the right download? | Authenticated/public byte regression tests compare the entire decrypted output with the original fixture. | A rendered button or successful login is not download completion. ZIP failure must not claim a ZIP was created. |
| Which credential is needed? | `file-credential.ts`, legacy File Request salt adapter, account envelope version, session-vault and preview worker. | Original file password for legacy/request files; account PIN for supported account/RSA/Drop paths; unlocked folder key for folder files. Do not infer file encryption from current account PIN settings. |
| Does account recovery recover every file? | Custodian reconstruction restores the account RSA key. Legacy owner files may be derived from the old PIN/password. See `credentials-and-recovery.md`. | Explain original-credential, backup or sender options before and after reset. A replacement PIN is not proof that old PIN-derived files can decrypt. |
| Does empty history mean no one accessed it? | Timeline endpoint reconstructs current records; deleted grants can disappear, and legacy closure times are unavailable. Lookup failure or an empty result is not proof of no access. | Label a reconstructed activity snapshot; consult current permissions. Hide unsupported closure timestamps. Never fabricate an owner-only history. |
| Does a local signature prove authenticity? | Preview signs/verifies exact bytes against this account key and browser-local signature storage. | A local byte comparison does not independently establish sender identity or legal non-repudiation. Keep signing in advanced details. |
| Does green service status prove every action works? | `/api/healthz` measures response and database ping. Readiness and per-file operations are different checks. | API/database responded; individual actions may still fail. Unknown build identity stays unknown. |

## Verification and remaining gates

- Unit tests cover rejected revoke, owner/intake count exclusion, history uncertainty, credential selection, future dates, and real Drop/RSA/legacy/folder preview bytes.
- Private Playwright journeys establish byte integrity and recoverable wrong credentials. Fixture contrast/navigation tests establish only the rendered states they exercise.
- No claim in this table replaces human unassisted trials, physical-device/passkey acceptance, a production release check, or operator restore/reboot evidence.
- Security iteration 6 must verify that server access aggregation, mutation atomicity, credential lifecycle and logging meet these visible contracts. Keep any outstanding server finding explicit until its negative test passes.
